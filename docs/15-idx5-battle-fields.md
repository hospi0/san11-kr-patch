# 15 — idx5(단일전투/결전 데이터) 부분 해독 (2026-07-18 세션12 계속)

> 사용자가 PC판(`KOR_도원결의_111009/Media/scenario/scenario.s11`, 47,800B — **idx5와 바이트
> 크기 완전 일치**)과 비교하며 "우리 TSV가 너무 작다"고 지적 → idx5를 다시 파서 실제로
> 캠페인 컨테이너(docs/14)와는 **완전히 다른 포맷**이며 새 번역 대상이 있음을 확인했다.

## 정체: 결전(전투) 모드의 지형·시설·공성병기·계급 데이터 풀

idx5는 도시명 테이블(앞부분, 0x5a~0x730 대) + **결전 전용 필드 오브젝트/시설/병기/관직 설명
풀**(뒷부분, 0x730~ 끝)의 두 구획으로 보인다. 캠페인 컨테이너의 깔끔한 null-종료 구조와 달리
**이진 스탯 필드와 텍스트가 null 구분 없이 붙어 있어** 단순 null-split로는 문자열이 깨진다
(세션 초반의 최초 스캔이 이 함정에 빠져 "石壁"이 "쓰지 못하는 조각글자"로 나왔던 원인).

### 발견된 콘텐츠 예시 (정제 후)
```
0x0cba 周囲２マスにいる味方部隊の防御力増加          (지형효과)
0x0eee 部隊の進行を阻む壁。土塁より固い              (石壁 설명)
0x11de 周囲２マスに引火する火罠                      (화계 함정)
0x158a 万里の長城。中国四千年の歴史                  (PK보너스 건축물)
0x18de 木獣、井闌、引火しながら３マス転がる           (공성병기)
0x23b2 騎兵に有利だが、戟兵に不利                    (병과 상성)
0x2996 塔楼船を強化した艦船。投石攻撃が可能            (수군 함선)
0x2d96 市場の３倍の金収入。造幣効果なし               (시설 등급별 효과)
0x362e 武庫令 / 0x368a 牙門将軍 / 0x2e92 偏将軍       (관직명)
```
→ **전투(결전) 화면 전용 지형지물·공성병기·수군함선·시설등급·관직**. 지금까지 번역한
"시설효과 47종"(전략맵용)·"관직 80종"(entry5)과는 **다른 풀**(관직명은 문자열이 겹칠 수
있으나 위치·용도가 다름 — entry5_names.tsv 대조 결과 이 관직명들은 거기 없음, 별도 확인 필요).

## 구조 — 부분 해독, 완전하지 않음

- **마커 바이트 `0x07`이 종종(전부는 아님) 설명문 직전에 온다** — 27건은 정확히 맞았지만
  전체 설명문의 절반가량은 07 마커와 텍스트 사이에 가변 길이(0~3B)의 잔여 바이트가 더 있다.
  → **레코드 헤더 길이가 가변**이라는 뜻(항목마다 붙는 이진 필드 개수가 다름).
- **최선 결과**: null-구분 청크마다 오프셋 0~30을 순차 시도해 "PUA/제어문자/반각가나로
  시작하지 않고 끝까지 깨끗이 디코드되는 지점"을 찾는 휴리스틱(`clean_start`, 세션 스크립트,
  파일로 저장 안 함) → **411개 후보 / 5,838자** 회수. 그러나 여전히 10~20%는 앞머리 1~2글자가
  덜 잘린 채 남아있다(예: "蘭h御力に優れた拠点"의 "蘭" · "行圏ﾗ接マスの敵部隊を混乱させる"의
  "行"). **완전 정확한 레코드 파서는 아직 없다.**
- **참고: 정확한 재주입(패치)에는 이 휴리스틱으로는 부족하다** — 추출은 근사치로도 번역
  참고용으로 쓸 수 있지만, 실제 게임에 되쓰려면 레코드 경계를 바이트 단위로 정확히 알아야
  한다(entry5 "널 따라 걷는 파서 금지" 교훈과 동일한 함정 — 지금 상태는 아직 그 수준 미달).

## 세션12 3차: 정확도 개선 + 파일 전체 지도 확정

### 발견 1 — "off-by-one 잔여바이트" 패턴 규명
`clean_start` 휴리스틱이 종종 진짜 텍스트 앞에 **엉뚱하지만 유효한 한자 1글자**를 붙여 뽑았다
(예: "蘭防御力に優れた拠点"에서 "蘭"은 진짜와 무관 — `防御力に優れた拠点`.encode('cp932')와
정확히 일치하는 바이트열 앞에 단독 바이트 `0x97` 하나가 끼어있었을 뿐). **한 오프셋이 "유효하게
디코드된다"는 게 "그게 진짜 시작점"이라는 뜻은 아니다** — 우연히도 그 앞 잔여바이트가 실존하는
한자와 우연히 일치하는 경우가 많다(전체 한자셋이 크기 때문에 우연매치 확률이 낮지 않음).
→ **화이트리스트 기반 재정렬**: 지금까지 확인된 "문장이 실제로 시작하는 단어"(周囲·隣接·部隊·
引火·技巧·金、·兵士·軍事の·耐久·強化した·楼船·市場·農場·万里·毎月·ＯＣ 등 약 50개)로 후보
오프셋 중 그 단어로 "시작하는" 것을 우선 채택 → **410개/5,447자**로 정제(화이트리스트 미매칭
139건은 여전히 불확실, 폴백 유지). 여전히 완전하지 않다 — 근본적으로 **레코드 헤더 길이 규칙을
모르는 채 통계적으로 추정하는 한계**다.

### 발견 2 — 파일 전체 지도 확정 (CJK 밀도 블록별 측정)
```
0x0000~0x0730  도시 42곳 이름+읽기 (지명은 이미 번역됨 — 재사용)
0x0730~0x2d00  지형/시설/함정/공성병기 설명문 (신규, 위 411개/5,447자 대부분 여기)
0x2d00~0x5000  관직·작위 이름+읽기 테이블 대량(「○○ショウグン」류 반복) —
                일부는 기존 작위10과 실제로 겹친다(**五官中郎将=ゴカンチュウロウショウ**
                확인, RANKS 딕셔너리에 이미 "오관중랑장"으로 번역됨) → 상당수 **재사용 또는
                자동 독음 변환**(`kr_names.to_hangul`)으로 처리 가능할 가능성, 전수 대조 필요
0x5000~0x8000  위와 비슷한 밀도의 두 번째 구획(石壁 등 명칭 재등장하나 **바이트 동일한 중복은
                아님** — 독립된 별개 레코드로 확인, 대조 실험으로 확정) — 성격 미상, 후속 조사
0x8000~0xbab8  CJK 문자 밀도 0 — **순수 이진 데이터**(지형그리드/유닛배치 좌표로 추정, 텍스트
                없음, 번역 대상 아님)
```

### 세션12 4차: `0x07` 마커 가설 — **반증됨**
전체 120개 표본으로 재검증: 텍스트 시작 직전 10바이트 안에 `0x07`이 있는 경우가 **19/120뿐**
(나머지 101개는 근처에 07 자체가 없음). 처음 몇 샘플에서 우연히 07이 여러 번 걸려 "마커"로
착각한 것 — **표본 편향**([[feedback_scan_coverage_and_detectors]] 세 번째 재발). 있는
19건 중에서도 07 직후 바로 텍스트인 경우(residue=0)는 12건뿐이고 나머지는 1~9바이트의
잔여물이 더 있어 규칙성이 없다. **→ 순수 통계·휴리스틱으로 헤더 스키마를 알아내는 시도는
막다른 길에 도달했다.** 다음 단계로 나아가려면 **SLPM 실행파일에서 이 파일을 읽는 루틴을
디스어셈블해야 한다**(LS11급 작업 — 단 LS11 때와 달리 이번엔 **참고할 외부 레퍼런스가 없다**,
kaodata 같은 선례 없이 처음부터 풀어야 함 → 비용·불확실성 더 큼).

### 최종 평가
- **신규 번역 필요량 ≈ 5,000자대**(지형/시설/함정/공성병기 설명, 0x0730~0x2d00 구간).
- **관직·작위 테이블**은 새 번역보다는 **기존 번역 재사용/자동변환** 쪽에 가깝다(전수 대조는
  다음 세션 과제).
- ⛔**여전히 "안전한 재주입" 수준은 아니다** — 레코드 헤더의 정확한 바이트 규칙(가변 길이가
  왜 가변인지)을 모른 채 통계적 재정렬로 뽑은 텍스트라, **번역 참고 자료로는 쓸 수 있어도
  게임에 그대로 되쓸 순 없다.** 진짜 안전한 파이프라인을 만들려면 SLPM에서 이 파일을 읽는
  루틴을 찾아 헤더 스키마를 확정해야 한다(LS11 때와 같은 종류의 작업, 이번엔 비압축이라
  크립 없이도 실마리를 잡을 여지가 있다 — 예: 헤더의 마지막 필드가 "이어지는 정수 리스트의
  개수"일 가능성, `0x07`이 실제로는 "리스트 길이=7"일 수도 있다는 가설 등 미검증).

## 세션12 5차: **완전 해독 + 번역 + 빌드 통합 완료** (Fable→Sonnet 인계)

### 돌파구 — SLPM 디스어셈블 없이 푼 방법: PC JPN↔KOR 바이트 diff를 구조 오라클로
LS11처럼 kaodata 같은 외부 레퍼런스는 없었지만, **PC판이 JPN 원본과 KOR(도원결의) 번역본을
둘 다 갖고 있다는 게 대체 레퍼런스가 됐다.** `scenario.s11`(idx5와 바이트크기 완전 일치)의
JPN↔KOR diff를 뜨면 **"바뀐 구간 = 텍스트 필드, 안 바뀐 구간 = 이진데이터"**가 그대로
드러난다. ★★**번역문 자체는 안 읽고 diff의 위치·길이 정보만 오라클로 썼다**(사용자 방침
"PC판 번역은 안 쓴다" 준수 — 남의 번역을 베낀 게 아니라 "여기가 텍스트다"라는 좌표만 얻었다).

### 진실: "가변 헤더"는 없었다 — 전부 **고정 오프셋 테이블**(특기/기교/능력과 같은 패턴)
diff 좌표를 stride 격자에 맞춰보니 세션12 4차까지의 "가변 길이 헤더"는 **옛 레이아웃 잔재를
헤더로 착각한 것**이었다. 진짜 스키마 3개 확정(60/12/20 레코드 전수 검증):
```
전장시설  base 0x0B82  stride 0xBD  × 60   +0x00 이름(cap8) · +0x09 읽기(불변) ·
                                            +0x1E 설명(cap~70) · +0x65 건설조건
병장      base 0x3AC2  stride 0x96  × 12   +0x00 이름(불변,기존커버) · +0x1A 설명
지형      base 0x8A54  stride 0x17  × 20   +0x00 이름(cap4=2음절) — 전법(0x8354+32*0x38) 바로 뒤
관직81번째           0x51E2 'なし'(관직80 배열 뒤 여분 슬롯)
```
전장시설 60개 = 都市·関所·港·陣·砦·城塞·弓櫓·連弩櫓·土塁·石壁·投石台·太鼓台·軍楽台·
石兵八陣·根城×2·火種~業火種(화계열 8종)·落石·堤防·浅瀬·山岳·長城·遺跡·廟·銅雀台·
시설Lv1~3(市場農場兵舎鍛冶厩舎)·고급시설14종.

2. **count=24의 의미** — idx5 헤더의 count=24가 "결전 시나리오 24종"을 가리키는지, 이 파일

   36,173자, 이미 e4_sys.tsv에서 처리됨)과의 관계도 미확정 — **중복 여부 확인 필요**.

## 결론
사용자 지적이 맞았다 — **idx5는 우리가 완전히 놓치고 있던 새 콘텐츠**(결전모드 지형·시설·
병기 설명, 최소 수천 자)이지만, **캠페인 컨테이너(docs/14)와 달리 아직 안전하게 추출·재주입할
수 있는 수준까지 해독되지 않았다.** 다음 세션에서 레코드 헤더 가변길이 규칙을 마저 풀어야
번역 파이프라인(추출→TSV→빌드)을 여기에도 만들 수 있다.

### 결론 — idx24~61은 **번역 파이프라인 대상에서 제외**
- 이 파일들 자체(3D맵·유닛배치·트리거 스크립트로 추정, 미해독)는 새로 팔 필요 없다.

  가능성은 완전히 배제 못 했다 — 전수 스캔은 아직 안 함(우선순위 낮음, 필요시 후속 확인).
