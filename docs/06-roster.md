# 06 — 무장 로스터 발견·해독·추출 (2026-07-17 세션2)

> 1순위 블로커였던 "800명 무장 로스터 미발견"을 **동적 RAM 덤프**로 해결.
> 정적 스캔이 4번 실패한 이유와 최종 스펙을 기록한다.

## 결론 요약

| 항목 | 값 |
|---|---|
| 위치 | `s11pkres.bin`, **모든 시나리오 파일에 임베드 = 52벌** |
| — 엔트리 6~21 | rel **0x3b75**(레코드#0 시작), 175KB 컨테이너 |
| — 엔트리 24~61+ | rel **0x48ec0 − 0x58**(이름 0x48ec0), 1.15MB 파일 |
| 저장 형식 | **무압축 SJIS + 가이지** → 직접 in-place 패치 가능 |
| 규모 | **900명**(이름 슬롯) + 250 빈슬롯(신무장 편집용) = **1150** |
| 디스크 레코드 stride | **0x98 (152 B)** |
| RAM 레코드 stride | 0xF0 (240 B) — 런타임 상태가 추가됨 |
| 정렬 | 카타카나 읽기순 (아 → 힌) |
| 검증 | 디스크 추출 vs RAM 추출 **900/900 완전 일치** |
| 추출본 | `work/roster_ram.txt` (TSV: idx·姓·名·字·읽기) |

## 이름 필드 레이아웃 (디스크·RAM 공통, 레코드 시작 기준)

```
+0x54  40 bb 5c 00       공유 포인터 0x5cbb40 (모든 레코드 동일)
+0x58  姓 (5 B)          SJIS/가이지 1~2자 + 널패딩
+0x5d  名 (5 B)          SJIS/가이지 1~2자 + 널패딩
+0x62  字(あざな) (5 B)   SJIS 2자 + 패딩 (없으면 전부 00)
+0x67  読み (카타카나)     null 종료
```

예 (레코드 #6 于禁):
```
40 bb 5c 00 | 98 b0 00 00 00 | 8b d6 00 00 00 | 95 b6 91 a5 00 | 83 45 83 4c 83 93 00
             于               禁               文則(字)         ウキン(読み)
```

## ★왜 정적 스캔이 4번 실패했나

**이름이 글자마다 3바이트 널패딩으로 저장된다.** `于` = `98 b0 00 00 00`, `禁` = `8b d6 00 00 00`.
연속 바이트 "于禁"(`98 b0 8b d6`)은 디스크·RAM 어디에도 존재하지 않는다 →
평문 SJIS 연속검색, 姓/名 분리검색, 슬롯 인덱스, 한자런 검출 **전부 빗나감**.

패딩된 14바이트 시그니처 `98 b0 00 00 00 8b d6 00 00 00 95 b6 91 a5`(于禁文則)로 검색하니
s11pkres.bin에서 **정확히 52회** — 시나리오 파일마다 1벌씩.

## 동적 규명 경로 (재사용 가능)

1. 세이브스테이트 `sstates/*.02.p2s`(武将情報 화면 = 무장DB 로드됨)를 `tools/p2s.py`로 추출 → `work/state02/eeMemory.bin`.
   ⚠️ `.01`(시나리오 선택 화면)은 무장DB 미로드 — 로스터 없음.
2. 화면에 보이는 선택 무장(于禁)을 RAM에서 SJIS로 검색 → 디스플레이 버퍼 `0x83bc50`에서
   포맷 문자열 `0a 00 00 00 | 于禁(文則)` 발견(길이프리픽스 + 이름+字 조합).
3. 읽기(`ウキン`)를 검색 → 로스터 본체 `0x1c2f560` 클러스터 발견.
4. 공유 포인터 `40 bb 5c 00`(레코드+0x54)를 앵커로 stride·개수 측정 → 0xF0 × 1150.
5. 패딩 이름 시그니처로 디스크 원본 위치 확정 → stride 0x98 × 900.

도구: `tools/analysis/{ram_name,ram_region,ram_density,ram_stride,find_roster,roster_extract}.py`

## 가이지 무장 67명 (글리프 보존 필수)

cp932로 인코딩 불가한 한자를 이름에 포함 → 게임이 가이지(char ≥ 0xF0xx)로 그린다.
`roster_ram.txt`에서 `[Gf0xx]`로 표시. 예:
- #8 衛`[Gf07d]`(瓘) 伯玉 エイカン
- #60 賈`[Gf049]`(詡) 文和 カク
- #144 許`[Gf05d]`(褚) 仲康 キョチョ
- #53/54 `[Gf044]`越/`[Gf044]`良(蒯) — 蒯越·蒯良
- #101~103 `[Gf07b]`丘倹/秀/甸(毌) — 毌丘 일족

⚠️ **이 가이지 슬롯 글리프는 고유명사에 실제 필요 — 한글 운반체로 회수 금지.**

## 한글화 시 주의 (필드폭 실측 완료 2026-07-17)

### ✅ 필드폭 = 문제 없음 (900명 전수 실측)
- 姓·名 각 **고정 5 B = 최대 2글자**. 900명 중 **5번째 바이트 non-null = 0개** → 한 필드에 3글자 들어가는 케이스 없음.
- 4글자 이름(木鹿大王·金環三結 등 78명)은 **姓2 + 名2로 분할** 저장 → 각 5B에 맞음. 姓+名 합계 최대 4글자.
- **한자 1자 = 한글 1음절 = 둘 다 2 B** → 한글 치환은 **바이트 완전 동일**. 같은 오프셋에서 1:1 코드 교체만 하면 됨. 필드폭·재배치·포인터 문제 전무.
  - 于禁→우금, 諸葛亮→제갈(姓)+량(名), 木鹿大王→목록(姓)+대왕(名), 賈詡(詡=가이지0xf049)→가+후 전부 원본과 동일 바이트.
- 가이지 이름 67명: 한글 치환 시 가이지 코드가 한글 운반체로 바뀌므로 **그 글리프를 이름용으론 보존 불필요**(단 산문·지명에 같은 가이지 잔존 시 거기선 필요 — 별건).

### 남은 실무 주의
- **52벌 전부 패치**해야 모든 시나리오 커버(빌드 스크립트에서 일괄).
- 읽기(카타카나) 필드는 리스트 정렬키 → 한글화 후 정렬이 일본어 가나순으로 남음. 한글 가나다순으로 자연스럽게 하려면 읽기필드도 손봐야 함(선택, 표시엔 무관).
- 표시용 "姓+名(字)" 문자열은 런타임에 로스터 필드에서 재조립됨(디스플레이 버퍼 0x83bc50) → **별도 풀네임 저장 없음**, 로스터 필드만 패치하면 리스트·상세 둘 다 반영.
